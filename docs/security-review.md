# Проверка безопасности текущей доработки

Проверены границы HTTP API, авторизация сайта и админки, связывание Telegram-аккаунтов, обработка внешних ссылок, сеть проверяющего процесса, очередь агентов и вывод данных в интерфейсе. Этот документ описывает исправления в коде и оставшиеся эксплуатационные условия. Он не означает, что у приложения не может быть других уязвимостей.

Рабочие учётные данные, production-БД и реальные Telegram-переписки для проверки не использовались. PostgreSQL-сценарии запускаются в отдельных временных схемах тестовой БД. Число пройденных тестов и результаты браузерной проверки фиксируются в отчёте о выполнении задачи.

## Исправленные пути атаки и ошибки доверия

| Область | Изменение |
| --- | --- |
| Регистрация | Публичная форма создаёт только новую веб-учётную запись. Нельзя назначить пароль уже существующей Telegram-личности, зная её username. Устаревшее потребление регистрации через Telegram отключено. |
| Логин | Вход привязан к `account_login`, а не к изменяемому Telegram username. Неоднозначные старые совпадения логинов не дают успешную авторизацию. Создание нового логина защищено транзакционной блокировкой. |
| Сессии | Подпись cookie дополнена проверкой существования пользователя и `session_version` в БД. Удалённый аккаунт и сессия до смены пароля перестают давать доступ. При недоступной БД защищённое API не доверяет одной старой подписи. |
| Связывание Telegram | Разрешён перенос веб-аккаунта с отрицательным ID к контролируемому пользователем Telegram ID. Передача уже привязанной положительной Telegram-личности другому ID запрещена. |
| Админка | Токен содержит случайный nonce и действует только в реестре выданных сессий процесса. Выход отзывает сессию, повторная подстановка того же cookie не возвращает доступ. |
| Подбор и проверка | Публичное API не соединяется с присланными пользователем host/port. Оно принимает известные ID каталога и лишь запрашивает ограниченное фоновое обновление. |
| SSRF | Проверяются буквальные IP и все DNS-ответы. Приватные, loopback, link-local, multicast, reserved и некоторые переходные IPv6-адреса запрещены. Соединение проверки привязано к проверенному публичному IP. Смешанный публичный/приватный DNS-ответ отклоняется. |
| Движок | Нативная библиотека работает в дочернем процессе с тайм-аутом и ограниченными JSON-сообщениями. Неверный протокол, зависание или авария не становятся положительным результатом. |
| Агенты | Нет публичного enrollment. У каждого заранее разрешённого узла отдельный Bearer-токен; в БД его SHA-256. Агент не получает задания на выполнение команд. |
| Результаты агентов | Результат связан с агентом, заданием, попыткой, секретом аренды, DC, сетевой эпохой и временем аренды. Устаревшая/заменённая аренда отклоняется, повтор принятого результата идемпотентен. |
| Достоверность выдачи | TCP/TLS, SNI, старые баллы и мнение пользователя не подменяют машинную проверку MTProto. Отозванный агент и старая сетевая эпоха не поддерживают текущую рекомендацию. |
| Обратная связь | Жалоба скрывает вариант только у отправителя. Массовые или случайные отметки не создают глобальный бан и не рисуют российскую проверку. |
| Браузер | Пользовательские значения экранируются, динамические действия прокси используют данные элементов и обработчики, ссылки ограничены допустимыми схемами/адресами. Отсутствующий `localStorage` не ломает интерфейс. |
| Ошибки | Клиенту не выдаются сырые SQL-ошибки, traceback, локальные пути и представления исключений. API-ответы не кэшируются. |

## HTTP и хранение паролей

Пароли хешируются PBKDF2-HMAC-SHA256: 600 000 итераций и отдельная случайная соль. Старый поддерживаемый формат проверяется для перехода; при входе возможен rehash. Хеширование вынесено из основного цикла asyncio. Длина входных паролей ограничена, регистрации и попытки входа ограничиваются по частоте.

Пользовательский cookie подписан, имеет срок 30 дней, `HttpOnly`, `SameSite=Lax` и `Secure` при HTTPS. Административный cookie имеет срок восемь часов, `HttpOnly`, `SameSite=Strict`, ограничение пути админки и `Secure` при HTTPS. Реестр админских сессий ограничен 128 записями. Локальные ограничители запросов также имеют верхнюю границу размера.

Middleware проверяет `Origin` и `Sec-Fetch-Site` для изменяющих запросов. Межсайтовые запросы отклоняются; исключение — Telegram webhook с отдельной проверкой секрета. Запросы клиентов без браузерных заголовков всё равно должны пройти соответствующую авторизацию.

Общий HTTP-лимит тела запроса — 128 KiB; API агентов дополнительно ограничивает тело 16 KiB. Используются заголовки `nosniff`, `X-Frame-Options: DENY`, `Referrer-Policy`, `Permissions-Policy`, а для настроенного HTTPS — HSTS. В HTML есть CSP, но пока остаются `unsafe-inline` для имеющихся скриптов и стилей. Это не строгая политика без inline-кода.

По умолчанию заголовок `X-Forwarded-For` не определяет адрес клиента, поэтому его произвольная подстановка не обходит ограничение входа. `TRUSTED_PROXY_HOPS` включается только для известной цепочки reverse proxy, которая правильно добавляет/перезаписывает forwarded-заголовки. Если сервер доступен напрямую в обход такой цепочки, доверять этим заголовкам нельзя. На одном внешнем IP несколько пользователей могут разделять общий лимит.

Параметры `BASE_URL`, `ADMIN_PATH`, `BOT_USERNAME` валидируются до запуска. Для HTTPS требуется длинный `SECRET_KEY`. Секрет webhook отделён от токена Telegram-бота; при отсутствии отдельного допустимого значения он выводится из ключа приложения. Webhook проверяет секрет, ограничивает незавершённые обработчики и повторные update ID; ошибка обработки даёт повторяемый ответ об ошибке вместо ложного подтверждения приёма.

## Доверенная зона частного агента

Токен агента разрешает получать задания и присылать результаты только от имени этой точки. Он не даёт административную сессию и не заменяет пароль аккаунта. Запросы идут по HTTPS; переадресации не выполняются. Планировщик и агент ограничивают пакет, число активных заданий, тайм-ауты и частоту проверок.

При этом владелец сервиса доверяет машине агента. Владелец токена технически может сфабриковать результат своей точки. Нет удалённой аттестации, подтверждающей, что агент действительно расположен у заявленного оператора и не изменён. Поэтому токены выдаются только собственным/доверенным узлам, а страна и тип сети задаются администратором. Публичный приём «проверок из России» от любых посетителей не включён.

`network_epoch` обновляется вручную при смене маршрута. При новом heartbeat с другой эпохой старые задания не принимаются и предыдущие наблюдения не участвуют в текущей выдаче. Если владелец забыл изменить эпоху при переходе на другую сеть, программной гарантии правильного сетевого описания нет.

`TDJSON_LIBRARY` позволяет загрузить нативную библиотеку из указанного файла. Это доверенная локальная настройка, а не пользовательское поле API. Загружать произвольный файл из непроверенного источника через неё нельзя: дочерний процесс не является полноценной изоляцией ОС от вредоносной библиотеки.

## Что проверяется автоматически

На 3 ноября 2026 года прошли 82 теста Python, включая настоящую временную PostgreSQL, и 81 проверка вёрстки Chrome в двух темах. Дополнительно проверены основной вариант с резервом, истечение подтверждения и пять инструментов админки. В `pip-audit -r requirements.txt` известных уязвимостей не найдено. Эти результаты относятся к локальному окружению и установленным версиям зависимостей.

Нативный TDLib 1.8.69 прошёл положительную проверку публичного MTProto-прокси. На том же адресе с изменённым секретом успех не подтвердился; обычный HTTPS-сервер также не получил положительный результат. Замеры выполнялись без Telegram-аккаунта и сообщений. Дочерний процесс получает системные переменные для загрузки библиотек, без токенов и ключей приложения.

Набор тестов покрывает подписи и версии сессий, недоступность удалённых аккаунтов, запрет захвата регистрации, отзыв админской сессии, межсайтовые запросы, входные ограничения, запрет произвольных сетевых целей и разрешение только публичных адресов. Отдельно проверяются канонизация секретов, срок доказательства, несовпадение сетевых контекстов, разнообразие резервов и отсутствие положительного результата из TCP/TLS.

PostgreSQL-тесты используют конкурентное получение заданий, повтор результата, замену аренды, смену эпохи, отзыв узла и сохраняемую ручную блокировку прокси. Миграции выполняются повторно для проверки идемпотентности. Браузерный сценарий проверяет сайт, формы входа, каталог и вкладки админки в светлой/тёмной темах на нескольких ширинах, а также кнопки инструментов на одноразовых данных.

Команды обычных тестов и проверки интерфейса:

```powershell
.venv\Scripts\python.exe -m unittest discover -s tests -v
.venv\Scripts\python.exe tests/frontend_smoke.py
```

Для настоящих транзакционных тестов задайте `TEST_DATABASE_URL` отдельной тестовой PostgreSQL перед первой командой. Тесты создают и удаляют только собственные случайно названные схемы. Не направляйте их на рабочую БД. Проверка Python-зависимостей выполняется отдельно через `pip-audit -r requirements.txt`; её результат относится к известным на момент запуска сведениям и не проверяет нативный код TDLib целиком.

## Условия эксплуатации и границы проверки

В рамках доработки не развёрнут реальный российский проверяющий узел и не проведён сетевой замер через российских операторов. Успешная загрузка TDLib и локальные тесты не заменяют такой замер. Отдельного контрольного канала Telegram, длительного sustained-теста и автоматической проверки смены внешнего маршрута в текущем агенте нет.

Ограничители запросов, персональные исключения и реестр админских сессий находятся в памяти одного процесса. Для нескольких экземпляров потребуется общий backend этих состояний и координация фоновых workers. Текущая конфигурация проекта рассчитана на один постоянно работающий экземпляр.

HTTPS, доверенная цепочка reverse proxy, закрытый доступ к PostgreSQL, резервные копии и секреты окружения на хостинге остаются настройками развёртывания. Эта проверка не подтверждала настройки реального хостинга и не была внешним пентестом production-сервиса.

Изображение для нового логотипа в доступных материалах отсутствует. Текущая иконка не заменена выдуманным изображением; это незавершённый пункт оформления, а не результат проверки безопасности.
