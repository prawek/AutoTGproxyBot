# Как устроен подбор прокси в текущей версии

Этот файл описывает работающий код. Предыдущий [проект архитектуры](proxy-selection-design.md) содержит идеи развития; реализованное поведение нужно сверять с этим документом и кодом.

Протокольная основа: [документация TDLib testProxy](https://core.telegram.org/tdlib/docs/classtd_1_1td__api_1_1test_proxy.html) и [реализация ProxyChecker с AuthKeyHandshake](https://github.com/tdlib/td/blob/master/td/telegram/net/ProxyChecker.cpp). Проверка не требует входа в Telegram-аккаунт.

Основной сервер остаётся в Орегоне. Он собирает ссылки и проверяет MTProto со своей стороны. Для российского подтверждения нужен отдельный узел в реальной российской сети. Код такого узла и закрытый API уже есть; российский узел в рамках этой доработки не развёрнут. Без него сайт и бот прямо пишут, что проверка выполнена из Орегона.

Система не использует голоса пользователей как основание общей рекомендации и не пытается угадать работу у российского оператора по модели телефона, SNI или открытому TCP-порту.

## Каталог, измерения и выдача

Три процесса идут независимо:

1. Сборщик получает ссылки из настроенных источников и Telegram-каналов, разбирает секреты и сохраняет варианты.
2. Локальный проверяющий процесс и подключённые частные агенты выполняют ограниченные проверки TDLib `testProxy`.
3. Сайт и бот читают сохранённые измерения через общий `app/proxy/selection_service.py`. Запрос рекомендации не запускает собственное сканирование сети.

Вариант определяется нормализованным адресом, портом и каноническими байтами секрета. Его ID — первые 32 шестнадцатеричных символа SHA-256 этого набора. Разные секреты на одном адресе остаются разными вариантами. Hex, Base64 и Base64URL одного секрета дают одну идентичность; регистр Base64 перед декодированием сохраняется.

Источник ссылки показывает происхождение записи. Он не подтверждает доступность. Повторный сбор ссылки обновляет время обнаружения, но не продлевает срок протокольного подтверждения. Само измерение тоже не превращает старую ссылку в недавно обнаруженную.

В PostgreSQL хранятся:

- `proxies`: варианты, источники, параметры и административное исключение;
- `probe_agents`: разрешённые владельцем узлы, хеши токенов и описания их сетей;
- `probe_jobs`: очередь заданий и отдельные попытки их исполнения;
- `probe_observations`: результаты с исходным временем измерения.

Кэш процесса обновляется из БД каждые 15 секунд. При временной ошибке чтения остаётся предыдущий снимок: его срок подтверждения продолжает истекать. Перезапуск приложения и загрузка из БД не обновляют `checked_at` и `valid_until`.

## Что считается подтверждением

Проверка идёт через нативный TDLib в отдельном дочернем процессе Python. Успех засчитывается только при ответе `ok` на `testProxy` для конкретных IP, порта, секрета и Telegram DC. В модели этот уровень обозначен `auth_key`. Для проверки не нужны пользовательский Telegram-аккаунт, код входа или отправка сообщений.

`tdjson==1.8.69` поставляет Python-привязку и нативную библиотеку; это отдельный пакет распространения движка TDLib. При необходимости можно задать собственную доверенную совместимую библиотеку через `TDJSON_LIBRARY`. Если библиотека отсутствует, не запускается или выдаёт ошибку API, результат остаётся `unsupported_checker` либо `engine_error`. Такой результат не считается успехом и не продлевает старый успех.

Открытый TCP-порт, TLS-соединение, похожий на обычный сайт SNI, рекомендация администратора и прежняя условная оценка транспорта не дают статус `verified`.

Каждое наблюдение содержит:

- время измерения и срок действия;
- фактический публичный IP и семейство IPv4/IPv6;
- Telegram DC, имя и версию движка, профиль клиента;
- `network_key`, `network_epoch`, страну и тип сети точки проверки;
- результат, уровень проверки и длительность полного теста.

Длительность теста — не ICMP ping и не чистый TCP RTT. В интерфейсе она подписана как время теста.

Для успешного измерения сервер устанавливает `valid_until = checked_at + 5 минут`. Агент не может произвольно прислать более длинный срок. Время допускается не более чем на 15 секунд в будущем и не старше пяти минут при приёме результата; часы узла должны быть синхронизированы.

Наблюдения сравниваются в контексте `(network_key, network_epoch, resolved_ip, ip_family, client_profile_id, dc_id)`. Более поздняя протокольная ошибка в том же контексте заменяет предыдущий успех при оценке текущего состояния. Сбой движка или контрольной инфраструктуры не выдаётся за доказательство поломки самого прокси. Из БД загружается несколько последних результатов каждого контекста, чтобы диагностическая ошибка не скрыла ещё действующий успех.

При сохранении нового DNS-набора локальной проверкой доказательство для IP, которого в этом наборе больше нет, не используется. Публичные IP проверяются до соединения, и TDLib получает конкретный проверенный IP. Один успешный адрес многозначного DNS-имени не означает, что проверены остальные адреса или другое семейство IP.

Состояния для пользователя:

| Статус | Значение |
| --- | --- |
| `verified` | Есть действующее протокольное подтверждение в указанном контексте. |
| `stale` | Был успех, но сейчас его нельзя использовать как свежее подтверждение. |
| `unverified` | Подтверждения протокола ещё нет. |
| `failed_here` | Последняя учитываемая проверка не прошла в проверенных условиях. Это не утверждение о всех сетях. |
| `pending` / `empty` | По выбранным условиям нет готовой рекомендации либо нет кандидатов. |

## Порядок выбора и резервы

По умолчанию рекомендация включает только варианты `verified`. Каталог может показывать ссылки без подтверждения, но отмечает их состояние. Явный служебный параметр `allow_unverified=true` допускает выдачу неподтверждённых вариантов с соответствующей меткой, если подтверждённых нет. Он не меняет их статус на успешный.

Сначала соблюдаются исключения пользователя, ручные блокировки, тип прокси и выбранная страна сервера. Страна сервера берётся только из поля `server_country`; доменная зона SNI для этого не используется. Если реальной информации о стране нет, строгий фильтр RU/EU такой вариант не пропускает. Автоматического снятия фильтров при пустой выдаче нет.

Затем учитывается близость точки проверки к выбранной сети:

| Приоритет | Основание |
| --- | --- |
| 6 | Российское измерение с точным совпадением конкретного `network_key`. |
| 5 | Российская домашняя сеть для Wi-Fi/проводного выбора либо мобильная сеть для мобильного выбора. |
| 4 | Другая российская домашняя или мобильная сеть. |
| 3 | Российская сеть датацентра. |
| 2 | Российская точка с неизвестным типом доступа. |
| 1 | Проверка за пределами России, включая Орегон. |

Совпадение типа доступа не доказывает совпадение оператора и маршрута пользователя. Подпись рядом со ссылкой сообщает место фактического измерения.

Если для явно указанного `network_key` есть более свежая неудача, иностранное подтверждение не маскирует её. Общие значения `wifi` и `cellular` не объединяют всех операторов в одну сеть: ошибка одного домашнего провайдера не запрещает вариант для всех домашних сетей.

Внутри одного уровня учитывается ручная рекомендация администратора, затем выбранная сортировка. Обычный порядок использует количество отдельных минутных окон с успешными измерениями за последний час, свежесть и длительность теста. Сортировка по свежести или времени теста меняет порядок внутри уровня. Закрепление администратором не оживляет устаревший вариант и не перекрывает отсутствие протокольного подтверждения. Число успешных окон — наблюдаемая история, а не процент вероятности успеха.

Возвращаются основной вариант и до двух резервов. Для резервов исключаются одинаковые endpoint, одна подсеть `/24` у IPv4 или `/48` у IPv6, а при известных данных — повторный ASN сервера. Если независимых вариантов меньше трёх, система возвращает столько, сколько есть. ASN проверяющего узла и ASN сервера — разные сведения; последний не угадывается.

Отметки «работает» и «не работает» меняют только персональные исключения пользователя в памяти процесса. Они не считаются российским машинным измерением, не дают глобальной блокировки и не переживают перезапуск как постоянная история.

## Расписание и ограничения нагрузки

Локальный сбор по умолчанию запускается раз в 180 секунд. Ручной запрос обновления не позволяет сократить интервал запуска сборщика ниже 30 секунд. Измерения работают независимо: повторная локальная проверка варианта обычно не чаще 180 секунд, пакет — до четырёх кандидатов. В нём есть место для давно не проверявшегося или нового варианта, поэтому популярность сервиса и отзывы для исследования каталога не нужны. Нативный движок выполняет проверки последовательно; тайм-аут одного локального задания — 12 секунд.

Планировщик удалённых проверок работает каждые 15 секунд. Он рассматривает только включённые здоровые узлы с heartbeat не старше 90 секунд, ставит ограниченную очередь известных вариантов и не дублирует активные задания. Это небольшая рабочая очередь, а не гарантия проверки всего каталога каждые три минуты. Ограничение агента по умолчанию — 120 начатых проверок за час.

У задания срок пять минут; аренда попытки — до 90 секунд. Агент получает максимум два активных задания. Повторная аренда создаёт новые `attempt_id` и `lease_token`; старый результат не принимается. После трёх попыток повторная аренда прекращается. Повторная отправка уже принятого результата идемпотентна: время успеха не обновляется.

Агент получает только известные варианты каталога и выполняет фиксированный тип `mtproto_check`. API не выдаёт команды оболочки, произвольные URL для скачивания или операции с файлами. Неверные и просроченные результаты отклоняются. Результат относится к выданному DC и времени аренды.

После смены `network_epoch` старые задания этой точки отменяются, а её наблюдения предыдущей эпохи остаются историей и перестают участвовать в выдаче. Аналогично исключаются наблюдения отключённого узла либо узла, у которого владелец изменил сетевые метаданные. Старые строки при этом не переписываются.

## Настройка сервера и российского узла

На основном сервере остаются обычные параметры проекта: `DATABASE_URL`, `SECRET_KEY`, `BASE_URL`, `BOT_TOKEN`, `BOT_USERNAME`, `TG_WEBHOOK_SECRET`, `ADMIN_PASSWORD`, `ADMIN_PATH`. `BASE_URL` должен указывать на HTTPS-origin без пути. Для HTTPS требуется `SECRET_KEY` длиной не менее 32 символов. `PROBE_REGION=us-oregon` — метка локальной точки; она не переносит проверку в Россию.

Установка и самопроверка движка:

```powershell
.venv\Scripts\python.exe -m pip install -r requirements.txt
.venv\Scripts\python.exe -m app.proxy.tdjson_helper --self-test
```

Самопроверка проверяет загрузку библиотеки и получение версии. Она не подтверждает доступность конкретного прокси.

Для частного российского узла сгенерируйте отдельный случайный токен:

```powershell
.venv\Scripts\python.exe -c "import secrets; print(secrets.token_urlsafe(48))"
```

Задайте в окружении **сервера** `PROBE_AGENTS_JSON`. Пример структуры, где значение токена необходимо заменить:

```json
[
  {
    "id": "ru-home-1",
    "token": "REPLACE_WITH_A_RANDOM_SECRET_AT_LEAST_32_CHARACTERS",
    "country": "ru",
    "network_key": "ru-home-provider-city",
    "access_type": "home",
    "region": "actual-region",
    "asn": "actual-network-asn"
  }
]
```

Страну, тип сети, регион и ASN задаёт владелец по реальному размещению узла. `access_type` принимает `home`, `mobile`, `datacenter`, `unknown`. ID и `network_key` содержат только латинские буквы, цифры, `_`, `-`, длина 1–64. Поддерживается до 20 узлов; у каждого отдельный токен длиной 32–256 символов. В БД сохраняется SHA-256 токена. Сам токен остаётся секретом окружения сервера и соответствующего узла.

На **компьютере в российской сети** установите зависимости проекта и задайте:

```powershell
$env:PROBE_SERVER_URL = 'https://your-service.example'
$env:PROBE_AGENT_TOKEN = '<тот же отдельный токен>'
$env:PROBE_NETWORK_EPOCH = 'home-route-2026-11-03-a'
$env:PROBE_MAX_CHECKS_PER_HOUR = '120'
.venv\Scripts\python.exe -m agents.probe_agent --once
```

Для постоянной работы уберите `--once` и запустите процесс своим менеджером служб. Входящий публичный порт агенту не нужен: он обращается к серверу по HTTPS, затем напрямую к проверяемому публичному прокси. `PROBE_SERVER_URL` не должен содержать путь, query, fragment, логин или пароль. HTTPS-переадресации не выполняются, чтобы токен не ушёл другому получателю. Не задавайте `FETCH_PROXY` как способ измерения российской сети: он относится только к скачиванию источников основным сборщиком.

При переходе с домашней сети на мобильную, смене VPN, внешнего маршрута или точки выхода остановите агент, обновите `PROBE_NETWORK_EPOCH` и при необходимости сетевые метаданные в `PROBE_AGENTS_JSON`, затем запустите снова. Автоматического определения нового маршрута по внешнему IP сейчас нет. Один узел должен иметь одно стабильное описание сети; не публикуйте один токен для произвольных пользователей.

Для отзыва удалите узел из `PROBE_AGENTS_JSON` и перезапустите сервер. Конфигурация окружения — источник разрешённых узлов, публичной регистрации агентов нет. В админке, во вкладке инструментов, показаны движок, агенты и состояния очереди без токенов.

| Переменная сервера | По умолчанию | Допустимый диапазон |
| --- | --- | --- |
| `PROXY_UPDATE_INTERVAL` | 180 с | 60–3600 с |
| `PROXY_CACHE_SIZE` | 300 | 20–1000 |
| `PROXY_RECHECK_INTERVAL` | 180 с | 60–3600 с |
| `PROXY_PROBE_BATCH` | 4 | 1–10 |
| `PROBE_AGENTS_JSON` | пустой список | до 20 узлов |
| `TDJSON_LIBRARY` | пакет `tdjson` | путь к доверенной совместимой библиотеке |
| `TRUSTED_PROXY_HOPS` | 0 | 0–5, только для известной цепочки reverse proxy |

`PROBE_MAX_CHECKS_PER_HOUR` задаётся на агенте: 1–1000, по умолчанию 120. Не увеличивайте лимит, чтобы компенсировать отсутствие проверок в другой сети: это не даёт новой географической информации.

## Переход со старой версии

При запуске приложение добавляет таблицы проверок и поля метаданных, блокировки и версии пользовательской сессии. Повторное применение миграций предусмотрено. Старые короткие ID прокси не используются как свежий каталог новой модели: ссылки будут заново обнаружены под каноническими ID и пройдут новую проверку. Старые баллы, `is_alive` и дата загрузки не превращаются в наблюдения `auth_key`.

Административное удаление создаёт сохраняемое исключение варианта: повторное появление той же ссылки у источника не возвращает его в выдачу. Плановая очистка старых записей не создаёт таких исключений. Наблюдения по умолчанию очищаются через семь дней, завершённые/истёкшие задания — после суток. Для выдачи загружается недавняя история, а не весь архив.

У пользовательских сессий проверяется `session_version` в БД. Смена пароля отзывает ранее выданные сессии; текущий веб-запрос получает новую. Административные сессии живут в реестре процесса и прекращают действовать при выходе или перезапуске. Устаревший сценарий регистрации через `reg_...` и polling регистрации выключен: он больше не может назначать пароль существующей Telegram-личности.

Перед обновлением рабочей БД нужна резервная копия, как перед остальными миграциями проекта. В существующей миграции пользователей также остаётся удаление старых платёжных таблиц и полей, относящихся к прежней модели подписки; эта доработка не добавляет платёжную систему.

## Границы текущей реализации

Российская доступность не выводится из сведений о блокировках, страны сервера или вида секрета. Её подтверждает только измерение частного узла в указанной сети. И даже такое измерение не обещает работу у всех абонентов этого оператора, в другом регионе, другом клиенте Telegram или через несколько минут.

Текущий агент проверяет инициализацию движка и доступность HTTPS API. Отдельной независимой контрольной проверки Telegram, автоматического обнаружения смены внешнего маршрута и длительного теста устойчивого соединения пока нет. Модель принимает уровень `sustained`, но штатный агент его не производит. Сетевые метаданные администратора не являются автоматической геолокацией.

Проверка использует профиль TDLib, конкретный DC и один IP за попытку. Клиенты Telegram и маршруты к другим DC могут вести себя иначе. Резервы снижают зависимость от одного адреса, но сами по себе не доказывают независимость операторов, если ASN сервера неизвестен.

Сбой проверяющего узла не должен превращаться в глобальный бан прокси. При отсутствии свежего доказательства система честно показывает ожидание или неподтверждённый каталог, вместо обещания «точно работает в России».

Описание текущих защит и проверок находится в [security-review.md](security-review.md).
