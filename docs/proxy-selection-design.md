# Подбор MTProto-прокси при основном сервере в Орегоне

Проект архитектуры, 3 ноября 2026 года. Основан на текущем коде AutoTGproxyBot и открытых первичных источниках. Описанные ниже изменения алгоритма и проверяющие агенты ещё не реализованы. Существующие браузерные и API-тесты не подтверждают доступность прокси из России.

## Решение для этого проекта

Оставить сайт, Telegram-бота, сбор источников, планировщик и PostgreSQL в нынешнем развёртывании Render Oregon. Отделить обнаружение ссылок от измерения их работоспособности. Выдавать рекомендации по сохранённым измерениям, а не запускать полный поиск при каждом нажатии.

Российские точки подключать постепенно как собственные доверенные агенты. Сервис должен нормально работать и без них, но тогда результат называется «MTProto проверен из Орегона; российская сеть не проверена».

Основной кандидат на протокольный движок — официальный TDLib `testProxy`. Решение о поставке TDLib в production принять после небольшого рабочего прототипа: проверить конкретную сборку, ресурсы, поддержку секретов, параллельные задания и запуск без аккаунта. Собственный FakeTLS не писать первым этапом.

Не нужны Redis, Celery, Kafka, отдельный кластер, машинное обучение или регистрация добровольных измерителей.

## Что можно и нельзя узнать

Предмет проверки — не «прокси вообще», а сочетание:

`вариант ссылки × фактический IP × сеть выхода × семейство IP × профиль клиента × DC Telegram × время`.

Один успешный результат не переносится автоматически на другую сеть, другой секрет или другую реализацию ClientHello. Отрицательный результат в российской сети не означает доказанную блокировку РКН. Это наблюдение об отказе конкретного соединения; причиной могут быть фильтрация, маршрут, сервер, DNS, часы или проверяющий клиент.

OONI показывает различия между российскими сетями, но его стандартный Telegram-тест проверяет доступность инфраструктуры Telegram и веб-версии, а не произвольные публичные MTProxy. Эти данные полезны для общего контекста, но не заменяют проверку кандидатов. [Отчёт OONI](https://explorer.ooni.org/findings/2026-russia-blocked-telegram), [спецификация теста](https://github.com/ooni/spec/blob/master/nettests/ts-020-telegram.md).

Разработчики Teleproxy описывают изменения клиентских отпечатков и различия поведения сетей. Их наблюдения стоит использовать как гипотезы для тестов, а не как полную спецификацию актуальных правил РКН. [Документация проекта](https://teleproxy.github.io/features/dpi-resistance/).

| Доступные условия | Что можно обещать в интерфейсе |
|---|---|
| Только Орегон | Конкретная ссылка прошла протокольную проверку из Орегона |
| Российский VPS | Прошла проверку из указанной датацентровой сети РФ |
| Одна домашняя точка РФ | Прошла проверку в этой домашней сети в указанное время |
| Домашняя точка и мобильный оператор | Есть отдельные результаты для двух сетевых контекстов |
| Несколько сетей и клиентских профилей | Можно подбирать по наиболее близким измеренным условиям |

Покрытие измерителей нельзя превращать в долю покрытия всей России. Два устройства за одним роутером — не два независимых сетевых подтверждения.

## Ошибки и искажения нынешнего алгоритма

| Место | Наблюдаемая проблема | Требуемое изменение |
|---|---|---|
| `pipeline._proxy_id`, `schema.make_proxy_id` | ID зависит только от host:port, хотя сбор различает секреты. В БД варианты перезаписывают друг друга | Новая идентичность конкретного варианта ссылки |
| `decoder.decode_secret` | Префиксы ee/dd проверяются до длины plain. 16-байтный plain-secret с таким началом отклоняется | Сначала интерпретировать длину декодированных байтов |
| `harvester._valid_secret` | Принимается только hex. Base64/base64url самого secret отклоняется | Поддержка форматов с канонизацией после декодирования |
| `selector.select_first_reachable` | TCP из Орегона и порог 350 мс определяют победителя | Пригодность по протоколу; задержка только дополнительный сопоставимый показатель |
| `pipeline._probe_tls_cover` | Проверяется обычный TLS, который может попасть на сайт прикрытия | Сохранить как отдельную диагностику; не считать подтверждением MTProto |
| `calculate_transport_score` | Базовые баллы за тип секрета и порт выглядят как измеренное качество | Исключить их из доказательности работоспособности |
| `MIN_TRANSPORT_SCORE=35` | Plain получает максимум 30 и всегда исключается, хотя присутствует в интерфейсе | Убирать по результату протокольной проверки, а не по недостижимому баллу |
| `CHECK_ROUNDS` | Три открытия TCP с паузой 0,1 с названы стабильностью | Отделить повторяемость одного запуска от истории во времени |
| `proxy_updater_worker` | Пустой `top` сохраняет прежний кэш; `LAST_CYCLE_AT` при этом обновляется | Считать свежесть каждого результата; старый успех не продлевать новым циклом |
| `_proxy_strikes` | Отсутствие в TOP считается отказом и может давать бан на шесть часов | Отсутствие в источниках/рейтинге не является измерением |
| `available_proxies`, `get_best` | Возраст проверки не ограничивает выдачу | Проверять срок действия при чтении, в том числе после рестарта |
| `filter.classify_domain` | RU/EU — доменная зона SNI, не география сервера | Переименовать профиль или убрать географическое представление |
| `personalization` | Бонусы FakeTLS/телефону/мобильной сети не основаны на российских измерениях | Сетевой контекст и клиентская совместимость вместо произвольных бонусов |
| `source_count` | Несколько URL могут быть перепостами | Хранить происхождение, не считать его независимыми успешными тестами |
| PostgreSQL | Не хранится полноценная история; часть признаков исчезает при рестарте | Сохранять наблюдения и восстанавливать из них выдачу |
| Отзывы | Двухнедельная агрегация без сети смешивается с краткосрочными банами в памяти | Отдельный слабый/личный сигнал, не основа российского рейтинга |
| Поиск по фильтрам | После неудачи фильтры могут сниматься автоматически | Строгие фильтры сохранять; расширять отдельным действием пользователя |

Это результаты чтения кода, а не измерения работающего production-развёртывания.

## Протокольный движок

### Почему сначала TDLib testProxy

Официальный `testProxy(proxy, dc_id, timeout)` допускает вызов до авторизации. В проверенном исходном коде он запускает `AuthKeyHandshake` с известными публичными RSA-ключами Telegram. Это сильнее, чем TCP и получение произвольного ответа. [Документация testProxy](https://core.telegram.org/tdlib/docs/classtd_1_1td__api_1_1test_proxy.html), [ProxyChecker.cpp](https://raw.githubusercontent.com/tdlib/td/master/td/telegram/net/ProxyChecker.cpp).

`pingProxy` оставить возможным дополнительным измерением задержки. Его не следует приравнивать к полному обмену ключами. Практический запуск выбранной версии без API-параметров и клиентской БД ещё предстоит проверить; одного указания «до авторизации» для такого обещания недостаточно.

У TDLib собственная реализация ClientHello с платформенными ветками. Она не тождественна автоматически Telegram Desktop, Android и iOS. В каждом наблюдении сохраняется точная версия и профиль движка. [Генератор TDLib](https://raw.githubusercontent.com/tdlib/td/master/td/mtproto/TlsInit.cpp).

### Уровни измерения

| Уровень | Доказательство | Ограничение |
|---|---|---|
| Синтаксис | Ссылка и секрет декодируются | Сеть не проверялась |
| TCP | Открылось соединение до адреса и порта | Секрет и Telegram не проверены |
| MTProxy/FakeTLS | Пройден соответствующий транспортный handshake | Ещё не подтверждён сервер Telegram |
| Быстрый MTProto | Корректный ответ на nonce в req_pq_multi | Сам по себе не полная аутентификация DC |
| Auth-key | Завершён проверенный обмен ключами с Telegram | Не доказана долговременная передача и медиа |
| Длительный тест | Проверена ограниченная серия обменов по соединению | Только проверенные операции и данный клиент |

В production предпочтителен уровень auth-key. Более слабые уровни сохраняются как диагностика и явно обозначенный fallback. Ошибка движка не понижает проверку до TCP с последующим зелёным статусом.

### Размещение и интерфейс

Движок работает отдельным долгоживущим процессом. Python общается с ним по JSON через stdin/stdout или локальный сокет. Нативная библиотека не загружается в процесс сайта и бота: сбой движка не должен останавливать HTTP/webhook.

Задание содержит явный объект прокси. Не переключать глобальный `enableProxy` при каждой проверке — параллельные задания не должны влиять друг на друга. Ограничивать параллельность внутри движка и внешний дедлайн в планировщике. Перезапускать зависший процесс с backoff; до self-test он считается нездоровым.

Точный состав полей запроса TDLib генерировать по закреплённой версии её схемы. Не копировать старые примеры с другой сигнатурой API.

### Приёмка прототипа

До интеграции в основной конвейер проверить:

- известный рабочий прокси, неверный секрет на том же адресе, обычный HTTPS-сервер и недоступный адрес;
- plain, dd и ee, включая plain-secret, начинающийся с ee/dd;
- эквивалентные hex/base64/base64url представления без изменения регистра до декодирования;
- доменное имя, несколько A/AAAA, отказ IPv4 при работающем IPv6 и наоборот;
- два параллельных разных прокси: результаты не смешиваются;
- работу без пользовательского аккаунта и все реально необходимые параметры инициализации;
- соблюдение дедлайна, восстановление после сбоя и отсутствие утечки процессов/дескрипторов;
- CPU, максимальный RSS, длительность и байты одной проверки на существующем тарифе Render;
- второй DC. Ошибка одного DC не объявляет весь прокси нерабочим;
- сравнение с актуальным официальным клиентом из той же российской сети.

Если упаковка TDLib слишком тяжела, можно сравнить готовый небольшой checker с TDLib как эталоном. До проверки кода и отрицательных контрольных примеров заявления README не считаются доказательством качества. Собственная криптографическая реализация остаётся последним вариантом.

## Идентичность ссылки и DNS

Логически различать endpoint и variant. Отдельная таблица endpoint для MVP необязательна.

- `endpoint_key`: нормализованный hostname/IP и порт.
- `variant_fingerprint`: полный SHA-256 от однозначно сериализованного endpoint и декодированных байтов секрета. Семантика транспорта входит в интерпретацию этих байтов.
- `variant_id`: короткий публичный идентификатор, например UUID или 128-битный случайный ID. Полный fingerprint остаётся уникальным в БД.
- SNI хранить как извлечённые метаданные. Не переписывать выданный секрет ради красивого имени домена.
- В hex регистр букв незначим; в base64 значим. Сначала определить и декодировать формат, затем строить fingerprint.

Публичный ID должен помещаться вместе с префиксом в Telegram callback. Полный SHA-256 в hex уже занимает 64 символа и для существующего формата кнопок неудобен.

Домены разрешает сама проверяющая точка. Наблюдение содержит DNS-ответ, фактический peer IP и семейство адресов. Успех на одном IP не делает все адреса за hostname проверенными. При изменении набора адресов сохранять старую историю, но понижать уверенность в текущем DNS-наборе до перепроверки.

Не считать отсутствие одной записи A/AAAA глобальным отказом при доступном другом семействе. Если часть опубликованных адресов проходит, а часть нет, показывать частичную доступность. Выдача закреплённого IP вместо hostname — отдельная политика: она меняет пользовательский маршрут и должна быть снова проверена, а не подставляться незаметно.

## Наблюдения и состояние

Одного `is_alive` недостаточно. Источник истины — факты проверок и их возраст.

В наблюдении нужны:

`job_id`, `attempt_id`, `variant_id`, `agent_id`, `network_epoch`, страна, ASN, тип доступа, фактический IP/family, `engine_name`, build/commit, `client_profile_id`, DC, уровень теста, достигнутый этап, исход, код ошибки, монотонные длительности, время начала, время приёма, состояние контрольных проверок.

Не все этапы движок отдаст с первого дня. Если известен лишь общий auth-key outcome и полная длительность, так и сохранять. Не выдумывать TCP latency из общей длительности handshake.

Пример исходов:

- `success`;
- `dns_error`, `connect_timeout`, `connection_refused`, `reset`;
- `proxy_handshake_failed`, `auth_key_failed`, `invalid_response`;
- `unsupported_checker`, `engine_error`;
- `agent_unhealthy`, `control_failed`, `cancelled`, `lease_expired`.

Ошибки настройки, неподдерживаемый checker и отсутствие результата не являются отрицательными измерениями кандидата.

| Состояние evidence в конкретном контексте | Условие |
|---|---|
| `verified` | Есть достаточно свежий успех и нет более нового валидного отказа |
| `failed_here` | Последний валидный результат — отказ именно здесь |
| `degraded` | Есть перемежающиеся успехи/отказы либо неполное покрытие адресов/DC |
| `stale` | Успех был, но срок действия истёк |
| `unverified` | Подходящего измерения ещё нет |

Новое валидное отрицательное измерение сразу снимает прежний зелёный статус в том же контексте: variant, фактический IP/family, сеть, клиентский профиль и DC. Для длительного карантина потребуется повторение с разносом во времени. Успех другой сети сохраняется независимо.

Уровни доказательств сравниваются по смыслу. Отказ обычного TLS-прикрытия не отменяет успешный auth-key тест MTProto. Успешный TCP не восстанавливает статус после отказа MTProto. Неудачное TCP-подключение может означать отказ нового протокольного теста, но отменяет подтверждение только соответствующего адреса/маршрута, а не всех IP и сетей.

`last_seen_at` обновляется только при фактическом обнаружении ссылки. Исчезновение из канала не продлевает его и не меняет состояние протокола. Сбой источников не продлевает срок прежнего успеха. Новый завершившийся цикл не меняет свежесть старого observation.

## Проверяющие точки в России

Первый агент — обычный Linux/Windows-компьютер на домашнем интернете. Переносить сайт или покупать российский сервер для этого не требуется. Малый роутер и самостоятельный Android-агент требуют отдельной упаковки движка и поддержки; это не лучший первый этап.

Вторая полезная точка — другой тип доступа и другой оператор. Временная проверка через USB-модем/раздачу с SIM тоже полезна. Её нельзя маркировать мобильной только из-за наличия SIM: трафик действительно должен идти через сотовую сеть.

Агент сообщает заявленный и наблюдаемый выход. При смене фактической сети/маршрута, интерфейса, ASN или включении VPN создаётся новая `network_epoch`. Семейство IP конкретной проверки и профиль движка хранятся отдельно: чередование IPv4/IPv6-заданий не должно само по себе создавать новую epoch. Если однозначно определить маршрут нельзя, измерение получает неизвестный тип сети. VPN-туннель не моделирует исходный доступ абонента.

Первую поставку агента сделать в двух режимах: одноразовая проверка ограниченной пачки и постоянный режим. Ручной запуск уже даёт полезные измерения; круглосуточный демон не является условием первого результата. Запуск на телефоне можно первоначально заменить компьютером с раздачей через SIM, проверяя действующий маршрут.

Российский VPS — дополнительный датацентровый контекст. Не объединять его с домашними измерениями под одним зелёным флагом «Россия».

Туннель с российским выходом может подтвердить доступность из его выхода, но длительность включает путь Орегон→выход. Такой результат нельзя показывать как локальный российский пинг.

### Контроль самого агента

Перед началом серии и после подозрительной пачки отказов проверять:

- доступность собственного API/других разрешённых контрольных HTTPS-целей;
- работоспособность DNS;
- часы и self-test движка;
- несколько ранее проверенных независимых прокси, если они есть.

Контрольные прокси тоже могут перестать работать. Массовый отказ MTProto при работающем обычном HTTPS означает проблему этого протокольного маршрута или контрольного набора; он не доказывает поломку всех серверов по отдельности.

Хранить исходные неудачи, но не начислять глобальный штраф всему каталогу при сбое агента. Прежние успехи всё равно стареют и перестают быть зелёными. После сна компьютера или смены сети сначала повторять контроль, затем брать новые задания.

Из российского агента отдельно проверять доступность домена сайта и API. Пользователь с неработающим Telegram может не получить ответ бота; веб-путь подключения остаётся самостоятельным.

## PostgreSQL и очередь

Для одного Render-процесса достаточно существующего PostgreSQL и нескольких таблиц.

| Таблица | Назначение |
|---|---|
| `proxy_variants` либо новая версия `proxies` | Идентичность, исходный секрет, транспорт/SNI, endpoint, first/last seen, административная блокировка |
| `probe_agents` | Токен агента в виде проверяемого хеша, возможности, сеть/epoch, heartbeat, версия |
| `probe_jobs` | Кандидат, агент/класс точки, профиль, DC, приоритет, срок исполнения, lease, номер попытки |
| `probe_observations` | Неизменяемые результаты попыток и контекст измерения |

Происхождение ссылок сначала можно хранить компактным JSONB. Число источников не участвует в уровне доказательности. Отдельные таблицы publishers/source appearances нужны лишь при реальной потребности в аналитике источников.

Старые процедуры `purge_old_dead`/`cap_proxies` нельзя автоматически применять к новой модели как к прежним строкам: они могут удалить активный вариант вместе с его историей или заданием. Варианты сначала выводятся из активного каталога; история очищается по отдельному retention. Удаление/запрет отменяет ещё не начатые задания этого variant. Физическую очистку и связи FK определить явно, без случайного каскадного удаления evidence.

Выдача использует небольшой snapshot в памяти, восстановимый из PostgreSQL. В нём обязательно сохраняются сроки действия: рестарт не делает измерение новым. Агрегирующая таблица в MVP не нужна; добавить её, если запросы последних observations станут узким местом.

### Жизненный цикл задания

`queued → leased → completed` либо `queued → leased → retry/expired/cancelled`.

Захват заданий атомарный, например транзакцией с `FOR UPDATE SKIP LOCKED`. Для получения небольшой пачки не держать транзакцию открытой на всё время проверки. Lease подтверждается отдельно; истёкший lease допускает повторную выдачу.

У каждой попытки новый `attempt_id` и `lease_token`. Ответ старой попытки не завершает новый lease. Уникальность результата по попытке предотвращает повторное начисление успеха. Обновление задания и запись принятого observation выполняются одной транзакцией.

Просроченный результат можно оставить в истории с соответствующим флагом, но нельзя использовать для текущего зелёного статуса. Сортировать факты по валидированному времени измерения, а не только по времени прихода: задержавшийся отчёт не должен перекрыть более новый отказ.

Сервер использует UTC для сроков; длительности измеряются монотонными часами агента. При сомнительных часах нельзя засчитывать свежесть задним числом. Конкретная политика допуска определяется тестами прототипа.

На Render нельзя использовать локальный файл как основной долговременный журнал: файловая система без persistent disk эфемерна. [Документация Render](https://render.com/docs/disks).

## API агентов и границы доверия

Агент инициирует исходящий HTTPS-запрос к Render. NAT и отсутствие публичного адреса дома не мешают. Для MVP достаточно индивидуального отзываемого токена и TLS с обычной проверкой сертификата.

Минимальные операции:

- `POST /api/probes/heartbeat` — возможности, версия, сеть и состояние агента;
- `POST /api/probes/claim` — получить небольшую пачку заданий с lease;
- `POST /api/probes/results` — идемпотентно отправить результаты своих попыток.

Названия — проект API, не существующие маршруты. Публичной регистрации агентов нет. Администратор заранее создаёт собственную точку; токен не даёт доступ к панели, пользователям или заданиям чужого агента.

Задание имеет фиксированную схему проверки прокси. Никаких shell-команд, Python-кода, произвольных URL для скачивания или удалённого обновления агента через эту очередь.

Ссылки берутся из внешних источников. Поэтому и сервер, и агент проверяют фактические адреса назначения: нельзя подключаться к loopback, private/link-local, multicast, служебным/metadata-адресам и адресам из DNS-rebinding. Проверка выполняется после DNS и перед соединением; подключение закрепляется за проверенным IP. Также ограничиваются число DNS-ответов, время, соединения и объём ответа.

Секрет нужен для теста, но его не следует печатать в обычные логи, telemetry или диагностические URL внешних сервисов. Учётные данные агента и клиентские auth keys не смешиваются с публичными proxy secrets.

Если Render недоступен, агент хранит только небольшой ограниченный буфер уже назначенных результатов. После истечения lease новые проверки не продолжает бесконечно. Он сам по себе не является открытым прокси.

## Планировщик и бюджет

Нынешний полный цикл заменить независимыми ограниченными задачами asyncio:

1. Сбор источников и обновление first/last seen.
2. Первичная проверка новых/изменившихся вариантов из Орегона.
3. Обновление измерений небольшого активного набора в российских сетях.
4. Проверка резервов и исследовательских кандидатов.
5. Обслуживание очереди, истории и состояния агентов.

Активный набор формируется по нескольким ASN/подсетям, а не только по текущим первым баллам. Часть бюджета обязательно оставлять новым кандидатам; иначе ранний случайный набор навсегда монополизирует проверки.

Повторы после отказа выполнять с backoff и небольшим jitter. Десяток пользователей не создаёт десяток одинаковых заданий: дедупликация по варианту, точке, профилю, DC и временному окну. Запрос подбора повышает приоритет подходящих существующих заданий.

Начальные параметры, которые требуется проверить экспериментально:

| Параметр | Разумная исходная настройка |
|---|---|
| Сбор источников | Существующий интервал порядка 3 минут, независимо от длительности проверок |
| Активные российские кандидаты | 10–20 разнообразных вариантов на точку |
| Их перепроверка | Каждые 3–5 минут при достаточном бюджете |
| Резервы | Реже, например каждые 15–30 минут |
| Новые варианты | Отдельная квота, чтобы не забивать активный набор |
| Параллельность домашнего агента | Начать с 2 проверок; менять по фактической нагрузке |
| Срок российского зелёного статуса | Начать с 5 минут при обновлении раз в 3 минуты |
| Длительные/дополнительные DC-тесты | Только небольшая часть лучших кандидатов |
| Сырые observations | Например 7 дней; затем агрегаты при необходимости |

Это не установленные оптимумы и не SLA. Если доступен только один периодический мобильный агент, показывать время последнего реального измерения, а не обещать постоянную свежесть.

Проверка 20 вариантов из двух российских точек каждые 5 минут создаёт 11 520 результатов в сутки и 80 640 за неделю. Это арифметика количества попыток; фактические CPU, байты и размер индексов нужно замерить. Дополнительные DC и повторы увеличивают число попыток.

Не хранить полный packet capture каждой успешной проверки. Для ошибок достаточно ограниченного кода/этапа и небольшой выборочной диагностики. У мобильной точки собственные лимиты проверок и байтов за час/сутки.

## Подбор и ранжирование

### Контекст пользователя

Для пользователя значимы оператор/сеть, тип доступа, приблизительный регион и версия клиента. Браузерные `rtt/downlink/saveData` не измеряют путь до выбранного MTProxy.

На сайте можно предложить необязательный выбор «домашний / мобильный / не знаю» и оператора. Автоопределение ASN по входящему IP — подсказка с возможностью исправить, поскольку IP может принадлежать VPN. Заголовкам пересылки доверять только от известного reverse proxy.

Бот не получает IP пользователя из webhook: это соединение серверов Telegram. Нельзя выводить оператора из IP webhook. Для бота достаточно запоминаемого необязательного выбора сети; при неизвестной сети выдавать общий разнообразный набор.

Не нужно хранить полный IP пользователя ради этой функции. Сохранять только выбранный/полученный сетевой контекст и его происхождение.

### Порядок принятия решения

1. Проверить корректность variant, административные ограничения и строгие фильтры.
2. Собрать подходящие актуальные observations и сначала проверить достаточность протокольного уровня. Российский TCP-успех не является российским MTProto-подтверждением. Неподдерживаемый профиль остаётся неизвестным.
3. Применить более новые валидные отказы в совпадающем контексте.
4. Определить класс свидетельства: совпадающая потребительская сеть → другая потребительская сеть РФ → российский DC → Орегон → только TCP/непроверено.
5. Внутри класса сравнить устойчивость во времени, возраст успеха, полноту адресов/DC и затем сопоставимую задержку.
6. Подобрать основной вариант и два резерва с разными условиями отказа.

Если есть свежий отказ именно в целевой сети, успех в другом контексте не возвращает зелёный статус для этой сети. При дефиците варианты с конфликтами можно вынести в отдельный явно обозначенный fallback, а не смешивать с подтверждёнными.

Профиль клиента также имеет уровень соответствия: точный проверенный профиль, похожая реализация, универсальный TDLib, неизвестно. Чужой клиентский профиль — менее близкое свидетельство, а не автоматическая совместимость.

Резервы разнообразить по фактическому ASN/префиксу IP; для IPv6 выбирать соответствующую ему гранулярность, а не механически применять IPv4 /24. Различие SNI на одном IP не делает два сервера независимыми резервами. Если пул бедный, честно вернуть меньше разнородных вариантов.

Admin pin действует внутри класса пригодности и имеет причину/срок действия. Он не отменяет TTL или свежий отказ. Ручная блокировка — отдельное явное действие.

Отзывы не нужны для работы системы. «Не работает» может временно исключить вариант лично для пользователя и запланировать проверку, не баня каталог глобально. «Найти другой» — только запрос резерва, без отрицательного голоса. Нажатие подключения и открытие Telegram не считаются успехом.

Наблюдаемые 9 успешных запусков из 10 можно показывать как «9 из 10 проверок этой точки». Нельзя называть это 90% вероятности работы в России: проверки коррелированы, выборка ограничена. Частый агент не получает больше сетевого веса только потому, что присылает больше отчётов.

### Единый сервис для сайта и бота

Создать один `selection_service`; веб и aiogram получают одинаковую структуру результата. Убрать два варианта подготовки кандидатов и их повторный сетевой обход.

Результат содержит основной variant и резервы, применённые фильтры, класс evidence, сеть проверки, профиль движка, время успеха, valid_until, конфликты и машинные reason codes для интерфейса.

При свежем snapshot HTTP handler отвечает сразу. Если сведений нет, создаёт ограниченную приоритетную проверку и возвращает `pending`. Ограничить время ожидания, например несколькими секундами с последующим предложением обновить результат. Не перебирать 300 адресов внутри запроса.

Строгие фильтры автоматически не снимать. Если подходящих данных нет, предложить «Показать другие варианты» либо «Показать проверенные только из Орегона».

При недоступности БД можно временно отдавать ещё действительный RAM snapshot. Новые подтверждения не объявлять сохранёнными; прежние продолжают стареть. При рестарте и недоступной БД нельзя выдать пустую историю за свежую проверку.

## Интерфейс и администрация

Пользователю показывать происхождение результата:

- «Telegram через прокси проверен из Орегона, 2 минуты назад; сеть РФ не проверена»;
- «Проверен в домашней сети X, 3 минуты назад; профиль TDLib»;
- «Есть свежая неудача в выбранной сети»;
- «Российское подтверждение устарело».

Это примеры формулировок, не текущие факты. Не использовать флаги стран SNI как географию сервера. Скрыть сортировку по отсутствующим отзывам либо сделать её второстепенной. Общая оценка «100/100 обхода» не нужна.

Для админки нужны:

- состояние каждого агента, реальная сеть, профиль/версия и последние controls;
- число свежих подтверждённых вариантов по сети и по уровню теста;
- очередь, возраст просроченных заданий, повторы и истёкшие leases;
- карточка variant с историей по точкам, IP и DC;
- точная причина исключения, административная блокировка и ограниченный pin;
- ручная перепроверка variant/группы, пауза агента и общий бюджет;
- результаты сборщиков отдельно от результатов проверки прокси;
- доступность сайта/API из российских точек.

Кнопка «Обновить» ставит ограниченную работу в очередь, а не создаёт параллельный полный конвейер. После удаления нужно определить политику: «удалить запись» допускает повторное обнаружение; «исключить этот variant» создаёт tombstone. Нынешнее автоматическое повторное наполнение источниками нельзя выдавать за постоянную блокировку.

## Что делать без российских устройств

Внедрять протокольную проверку из Орегона, исправлять свежесть, идентичность и резервы. Это самостоятельно полезное улучшение, даже если российских точек пока нет.

Можно добавить публичную российскую TCP-проверку как отдельное слабое evidence, не передавая secret. Check-Host позволяет выбирать узлы, но проверяет доступность порта, а не работу Telegram через заданный секрет. Наличие и тип актуальных узлов надо проверять при интеграции. [API Check-Host](https://check-host.net/about/api?lang=en).

Обычный JavaScript страницы не заменит raw TCP-клиент MTProxy. Direct Sockets в Chrome относится к Isolated Web Apps, а не к обычному сайту. WebSocket пригоден лишь для серверов с соответствующим транспортом и не является универсальным способом теста произвольных MTProxy. [Документация Chrome](https://developer.chrome.com/docs/iwa/direct-sockets).

Стандартные публичные измерители с ping/TLS полезны для контекста, но не превращают TLS-ответ в результат MTProto. Покупку сети агентов/резидентских выходов рассматривать только после сравнения фактического покрытия и проверяемости выходов; конкретный провайдер здесь не выбран.

## Как проверить, что подбор стал лучше

При малой аудитории оценивать собственные будущие результаты, а не ждать голосов.

Записывать небольшой снимок решения: время, контекст, известные в тот момент результаты, выбранные варианты и версию алгоритма. Затем проверять рекомендации следующим измерением, которое не участвовало в выборе.

Полезные показатели:

- доля первых вариантов, прошедших следующее валидное измерение в указанной сети;
- доля наборов, где прошёл хотя бы один из трёх вариантов;
- доля выдачи со свежим подтверждением совпадающей сети и профиля;
- возраст последнего успеха и доля stale/unknown;
- время ожидания, очередь и расход проверок/байтов на пригодный вариант;
- число случаев, когда предложенные резервы оказались одним и тем же endpoint/ASN;
- доступность самого веб-пути из российских точек.

Отсутствующие измерения не включать в denominator как неудачные, но отдельно показывать их долю. Контрольный outage не маскировать удалением неудобных результатов из отчёта.

При нескольких точках провести отложенный эксперимент: выбирать без данных одной точки и проверять на ней. Это покажет переносимость между имеющимися сетями. Такие цифры всё равно нельзя объявлять статистикой всей России.

## Этапы внедрения и критерии завершения

| Этап | Работа | Что считается завершением |
|---|---|---|
| 1. Исправить смысл данных | TTL, strikes, identity, secret decoding, Plain threshold, названия RU/EU, необоснованные бонусы | Старые/непроверенные ссылки больше не получают новый зелёный статус |
| 2. Прототип движка | TDLib testProxy, изоляция процесса, отрицательные controls, ресурсы | Измеренная совместимость и выбранный способ поставки на Render |
| 3. История и выдача | Observations, snapshots, единый selection_service, разнообразные резервы | Сайт и бот выбирают одинаково; результат объясним и переживает рестарт |
| 4. Одна российская точка | Агент, lease-очередь, network epoch, health controls | Есть протокольные результаты реальной потребительской сети РФ |
| 5. Второй тип доступа | Другой оператор/мобильная сеть, отдельный профиль | Успех одной точки не скрывает отказ другой |
| 6. Проверка качества | Отложенные замеры, длительные тесты и настройка расписания | Можно сравнить новый подбор с текущим по будущим результатам |

Этапы 1–3 не требуют российских устройств. Этап 4 зависит от реального доступа в российскую сеть: программный рейтинг эту зависимость не устраняет.

Миграцию проводить добавлением новых таблиц/полей. Старые отзывы, рекомендации и callback-ID относятся к host:port; их нельзя слепо переносить на новый секрет. Оставить legacy provenance. Старую кнопку разрешать только при однозначном соответствии, иначе предложить новую подборку. Сохранить возможность отката чтения на старый каталог до переключения выдачи; не смешивать его слабые признаки с новыми зелёными статусами.

Перед переключением запустить новый подбор в теневом режиме рядом со старым. Результат пользователю ещё не менять, а сравнивать пригодность, свежесть, расход и разнообразие. Конкретную длительность эксперимента выбрать по числу валидных измерений, а не по обещанию «достаточно одного дня».

## Обязательные сценарии проверки

- Пустой harvest не оживляет и не убивает старый вариант.
- Пустой список успешных результатов не продлевает прежний valid_until.
- Изменение secret/IP/family/профиля не наследует зелёный статус автоматически.
- Plain-secret с начальными ee/dd распознаётся по длине; base64 не меняется lower().
- Неверный secret на рабочем IP и обычный HTTPS-сервер не проходят auth-key тест.
- Отказ одного DC не объявляет отказ всех DC.
- Более новый валидный отказ снимает старый зелёный статус только в нужном контексте.
- Офлайн-агент, неподдерживаемый checker и timeout его процесса не банят каталог.
- Дублированный result не создаёт второго подтверждения.
- Поздний result не завершает чужой/новый lease и не перекрывает более новое измерение.
- Два потребителя очереди не получают одновременно один lease.
- Истёкшие задания восстанавливаются после рестарта Render.
- Строгие фильтры не снимаются fallback-поиском.
- Резервы не являются тремя разными секретами одного endpoint.
- Admin pin не обходит TTL и свежий отрицательный результат.
- DNS-rebinding/private IP/слишком большой ответ не позволяют агенту выйти за разрешённые цели.
- Сайт и бот возвращают одинаковый выбор при одинаковых данных и контексте.

Логику можно проверять unit-тестами и тестовыми репозиториями. Миграции, конкурентные leases и транзакционную идемпотентность нужно проверить на настоящей временной PostgreSQL. Сетевую корректность движка — известными контрольными серверами и российской точкой. Ни одна из этих проверок не заменяет другую.
